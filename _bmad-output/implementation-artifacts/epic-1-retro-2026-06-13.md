## What Went Well

- **Gate-first sequencing worked.** Three premise risks retired on hardware, not in a planning doc, before Epics 3/4 harden. Architecture's bet — gate outcomes *swap a module, not the architecture* — held (V1 → `ActivitySessionStrategy`; V2 → keep stock bridge; neither forced redesign).
- **Evidence-graded decisions.** OQ2 (Story 1.4) was resolved by disassembling SDK 2.0.3 / 2.2.0 / 2.4.0 AAR bytecode to map the three failure modes *before* sending — the 400/400 hardware result wasn't luck. ADR 0002 documents it.
- **`protocol/SPEC.md` is a real standard.** Numbered §1–§9, required/unused field matrix, worked byte-level examples both sides' tests pin against. Epic 5 only polishes it.
- **Mechanical drift detection.** Both `Protocol.mc` and `protocol_keys.dart` assert literal constant values and round-trip the same fixture bytes — drift fails a test, not a code review.
- **CI-in-the-exact-image discipline.** Verified in `ghcr.io/matco/connectiq-tester` (SDK 8.4.0), not just local SDK — this is how 1.2 caught the uncatchable `convertEncodedString` landmine local builds hid. Test-first (documented red phase) held every story.
- **Gates paid forward.** V1 handed Epic 3 a designed-for display reality (dims to LOW ~14 s, stays lit-dim for the hour) instead of a full-brightness surprise.

## What Was Challenging

- **The simulator/watchdog gap (the scar).** Story 1.5's first hardware sweep crashed the watch — `Watchdog Tripped Error — Code Executed Too Long` decoding a whole multi-KB chunk synchronously in the BLE callback. **Uncatchable, and invisible in simulator/CI** (the 8 KB fixture round-tripped clean in the test image). It was caught *incidentally* via the size sweep, not by a gate aimed at it. AR15 ("the simulator lies about the watchdog") went from prediction to scar. Watch unit tests provably cannot catch this class.
- **Over-claimed checkboxes.** 1.2 review: Task 1 `[x]` while 10/11 subtasks `[ ]` + mis-recorded test split. 1.3 review: outdoor legibility ticked but never performed; an invalid battery "measurement" (read 3 min after going on USB charge). The work was real; the bookkeeping over-claimed. The 3-layer adversarial review caught all of it before `done` — but it shouldn't take an auditor to keep our own checkboxes truthful. A trust problem more than a technical one (could have propagated unvalidated ground into Epic 3 UX).
- **Measurement validity on hardware runs.** The void battery reading nearly entered the record as evidence. On hardware, *how* you measure is as load-bearing as the code. Run B's watch ledger (1.4) was also destroyed by an accidental mid-run START press ~chunk 72 (phone-side accounting saved the measurement; drove the two-press-confirm + generation-tagged-ack hardening).
- **Evidence-retrieval friction (raised by Nerya).** Getting run results off the device meant reading the on-screen summary → messaging himself → copy-paste here — three manual hops for data already sitting in `flutter run` stdout. The single most annoying part of the epic.

## Key Insights

1. "The simulator lies" is no longer theoretical — hardware exposure for watchdog-class risk must be **deliberate**, not incidental.
2. Honest tracking is a trust asset, not bookkeeping; adversarial review is load-bearing.
3. The cheapest immediate win is human-in-the-loop ergonomics (evidence retrieval, measurement preconditions).
